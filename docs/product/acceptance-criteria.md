## 1. 文档目的与权威边界

本文件定义如何证明 `docs/product/PRD.md` 已被正确实现和交付。它不新增功能，也不替代后续 Product/System Design、Technical Architecture 或具体 Implementation Plan 中的测试清单。

规则如下：

1. 所有产品范围、用户结果和发布阻断项必须追溯到 PRD requirement ID 或明确章节。下游设计只能细化交互、实现和证据，不能独立新增产品范围；若产生新的产品发布阻断项，必须先修订并重新批准 PRD。
2. 若本文件与 PRD 冲突，以 PRD 为准，并修正本文件。
3. 单元测试、集成测试、E2E、性能测试和生产测试是证据类型，不是本文件的四个层级。
4. 四层验收是累积门禁；G1 分为实施前的产品定义门禁和投产后的业务价值门禁，避免用尚未实现的结果阻塞设计启动。
5. 未定义样本、环境、负载或判断口径的指标不得被临时宣告通过。
6. 任一必需证据缺失时，状态只能是“未开始”“进行中”或“阻塞”，不得使用“默认通过”。

当前批准边界（2026-07-31）：上游 PRD v1.1 与本四层验收标准已获产品负责人授权批准，G1-A 的产品定义门禁通过。销售/商务、市场研究、企业 IT、数据和安全等现实责任角色尚未具名；其签署仍是对应 G2、G3、G4 和 G1-B 的真实门禁，不能由 Codex 或产品负责人伪造，也不因 Foundation Task 获准而默认通过。

## 2. 四层验收模型

| 门禁 | 回答的问题 | 主要验收对象 | 必须批准角色 |
|---|---|---|---|
| G1 产品与业务验收 | 做的是不是正确的产品，是否解决目标用户问题 | G1-A：范围、角色和边界；G1-B：核心旅程、产品指标和试点价值 | G1-A：产品负责人；G1-B：产品负责人、销售/商务代表、市场研究代表 |
| G2 前端与体验验收 | 用户是否能清晰、高效、安全地完成任务 | 信息架构、页面、交互、状态、浏览器、可访问性、真实网络体验 | 产品负责人、业务代表、企业 IT |
| G3 系统与工程验收 | 系统是否按批准设计可靠实现并可持续演进 | 前后端、API、数据、权限、文件、测试、性能、安全、CI | 工程负责人、代码审查人、数据与安全负责人 |
| G4 生产与 Cloudflare 验收 | 产品是否已经在真实生产环境可用、可监控、可恢复 | Cloudflare 生产交付、域名、企业网络、生产数据链路、回滚、监控、试点 | 发布负责人、企业 IT、安全负责人、数据负责人、产品负责人 |

### 2.1 状态定义

每个门禁只能使用以下状态：

- **未开始：** 尚未进入验收。
- **进行中：** 已有部分证据，但全部通过条件尚未满足。
- **阻塞：** 存在明确失败、缺失批准人或尚未建立可判定基线。
- **通过：** 所有必需条件均有可复核证据，且没有未关闭的阻断项。

不使用“有条件通过”隐藏阻断项。非阻断问题可以形成已登记的后续改进，但必须由对应批准人确认其不影响本门禁。

### 2.2 顺序与累积关系

```text
G1-A 产品定义批准
    ↓
G2 前端与体验 ←→ G3 系统与工程（按产品域迭代）
    ↓
G4 生产与 Cloudflare
    ↓
G1-B 试点业务价值确认
```

- G1-A 通过后才能锁定页面和系统设计。
- G2 可以按产品域逐步完成，但完整产品 G2 需要所有核心旅程通过。
- G3 可以按 Implementation Task 或阶段逐步关闭子门禁，但完整 G3 需要所有产品域端到端联通。
- G4 只能针对真实 staging/production 环境关闭，localhost、dry-run、mock 或构建产物不能替代。
- G1-B 使用生产试点数据确认产品价值，只有 G1-A、G2、G3、G4 和 G1-B 全部通过，完整内部 MVP 才可最终验收。

### 2.3 门禁责任与签署规则

| 门禁 | Accountable gate owner | 必须签署 | 主要证据提供方 |
|---|---|---|---|
| G1-A | 产品负责人 | 产品负责人 | PRD、独立产品/一致性审阅、范围与边界记录 |
| G1-B | 产品负责人 | 产品负责人、销售/商务代表、市场研究代表 | 产品运营、业务测试参与者、市场研究 |
| G2 | 产品负责人 | 产品负责人、销售/商务代表、市场研究代表、企业 IT | 产品设计、前端工程、测试执行人、网络测试人 |
| G3 | 工程负责人 | 工程负责人、独立代码审查人、数据负责人、安全负责人 | 前后端工程、数据工程、测试与 CI 负责人 |
| G4 | 发布负责人 | 发布负责人、企业 IT、安全负责人、数据负责人、产品负责人 | 平台运维、发布执行人、监控与事故响应负责人 |

- Accountable gate owner 对门禁最终状态负责，但不能代替其他必须签署角色。
- 证据提供人和审批人必须记录姓名、日期和版本。
- 任一门禁要求的必须签署角色尚未具名或拒绝签署时，对应门禁状态为阻塞；G1-A 的签署要求不代替后续业务、工程或生产门禁的签署。
- Implementation Task 必须满足获批 Implementation Plan 定义的工程证据；只有该计划明确要求时，RED/GREEN、提交和代码审查才成为对应 Task 的强制制品。任何工程过程要求都不得改变 PRD 产品范围。

### 2.5 需求变更与门禁重开

- PRD 版本发生变化时，G1-A 自动从“通过”退回“进行中”，直到新版本完成批准。
- 产品负责人必须对变更的 requirement ID 做影响分析，列出受影响的 Product/System Design、Technical Architecture、Roadmap、Implementation Plan、代码、数据和 G1～G4 子门禁。
- 受影响门禁退回“进行中”或“阻塞”，重新提供证据并由原必须签署角色复验。
- 未受影响的旧证据只有在记录原需求版本、保留理由、适用范围和批准人后才可沿用。
- 任何受影响的上游文档或门禁尚未重新批准时，不得启动依赖它的新 Implementation Task。

### 3.2 必需证据

- 已签署并带版本号的 PRD。
- G1-A 的产品负责人批准记录；G1-B 的销售/商务与市场研究代表名单和签署记录。
- 版本化 UAT 任务脚本、测试数据、参与者和逐项结果。
- 会前准备任务的开始/结束时间记录。
- 经产品负责人和市场研究批准的代表性查询集、预期结果和人工判定记录。
- 已发布数据治理完整性审计报告。
- 权利与安全业务规则评审记录。
- 试点方案、用户范围、周期、产品分析结果和用户访谈纪要。
- 所有失败项、责任人、修复证据和复验结论。

G1-A 只需要范围、角色和边界批准证据；G1-B 需要产品实现和生产试点证据。G1-A 通过不得被表述为完整 G1 通过。

### 3.3 搜索成功率口径

`PRD-S-02` 的计算必须满足：

1. 查询集在测试前冻结并版本化。
2. 查询集覆盖公司、项目、报告、正文、别名、中英文、筛选和授权差异。
3. 每条查询预先标记预期存在结果或预期无授权结果。
4. 返回至少一个有用且授权正确的结果可以判为成功。
5. 仅当预期确实无授权结果时，清晰零结果与恢复路径才可判为成功。
6. 意外零结果、错误泄漏、错误权限或无用高排名结果不得计为成功。
7. 查询集规模、角色分布和判定人尚未批准时，G1-08 必须标记阻塞。

### 3.4 G1 阻断条件

出现任一情况即阻断：

- G1-A：PRD 尚未由产品负责人批准，或核心角色、功能范围、权限结果存在互相冲突的权威来源。
- G1-B：G2、G3 或 G4 尚未通过。
- 任一核心业务旅程失败。
- UAT 样本、参与者、完成定义或汇总规则未批准，或批准后的会前准备指标超过 5 分钟。
- 搜索查询集口径未批准或成功率低于 90%。
- 任一已发布生产记录缺失必备治理信息。
- 存在已知越权或受限内容误用。
- 敏感内容审核角色、授权数据内部使用许可或试点采用目标尚未在对应时点确定。
- 用基础框架、页面截图或单纯 page view 代替业务价值证据。

| 账号进入 | 已授权内部用户进入产品 | 未登录、账号禁用、会话失效 |
| 全局搜索 | 搜索并进入公司/项目/报告 | 零结果、服务失败、受限结果不泄漏 |
| 公司查找 | 搜索、筛选、查看关系和来源 | 数据缺失、陈旧、无权限字段 |
| 项目筛选 | 多条件筛选、查看详情和参与方 | 无结果、地图不可用、部分字段受限 |
| 报告使用 | 查找、预览、下载授权附件 | L3/L4 拒绝、权限收回或访问失效、预览失败 |
| 个人工作流 | 收藏、关注、保存搜索、查看通知 | 对象归档、权限被收回、通知目标不可访问 |
| 纠错 | 提交字段级纠错并查看结果 | 缺少证据、被拒绝、记录已更新 |
| 导入发布 | 上传、预览、校验、审核、发布 | 错误行、重复候选、权限冲突、发布回滚 |
| 管理与审核 | 角色允许时进入并处理任务 | 普通用户不可见或被明确拒绝 |
| 首页与最近使用 | 查看更新、收藏、最近查看和数据状态 | 无数据、部分数据受限、聚合失败 |
| 分享、导出与简报 | CSV/XLSX、PDF 简报和内部分享 | 权限收回、分享撤回/失效、受限字段被排除 |
| 通知治理 | 订阅保存搜索、静音、查看和处理通知 | 错误通知被抑制/撤回、目标失权 |

### 4.3 必需证据

- 带版本和批准记录的 Product/System Design 与信息架构。
- 每条核心旅程的测试账号角色、数据版本、步骤、原始结果和批准人。
- loading、empty、zero-result、error、401、403、404、账号禁用和撤权状态证据。
- 目标浏览器、操作系统、分辨率和响应式矩阵及逐项结果。
- 已批准可访问性基线及键盘、焦点、语义、对比度、缩放和读屏关键路径审计。
- 核心页面在企业网络的原始性能记录，包含环境、设备、版本、缓存和统计口径。
- 权限拒绝态、附件地址、敏感错误和结果数量不泄漏的体验证据。
- 关键运行时资源清单及目标网络可达性结果。
- 失败项、修复、复验和产品负责人签署记录。

### 4.4 性能测量要求

“核心页面可用”必须在 Product/System Design 或性能协议中定义为用户可以看到关键内容并执行主要操作，而不是只收到 HTML 或显示空壳。

测试报告必须记录：

- 办公地点、网络类型、测试日期和时段。
- 设备、操作系统、浏览器及精确版本。
- 冷启动或热缓存状态。
- 页面和测试账号角色。
- 已批准的样本次数、聚合方法和判定统计量；可以记录 P50、P75、P95，但必须事先明确哪一个用于 3 秒门槛。
- DNS、TLS、静态资产、API 和数据加载的分段结果。
- 失败、重试和不可访问第三方资源。

核心页面集合、冷/热缓存场景、样本次数、聚合方法或判定统计量任一未获批准时，即使单次加载低于 3 秒也不能关闭 G2-05。

### 4.5 G2 阻断条件

- 任一核心旅程无法完成。
- 任一权限拒绝态泄漏记录、片段、附件地址或敏感错误信息。
- 目标企业网络上核心页面未按批准统计规则满足 3 秒目标。
- 目标浏览器组合失败。
- 可访问性、响应式或浏览器基线尚未批准。
- 关键路径依赖目标网络不可访问的第三方资源。
- 只用本机 Chromium smoke、静态截图或组件单测替代完整体验验收。
