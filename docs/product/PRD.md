## 2. 产品摘要

Wison 已经拥有公司档案、项目地图、产量与财务看板、市场价格、行业报告库等原型与数据脚本。这些资产证明了内容价值和视觉方向，但当前信息分散在独立静态页面、文件、JSON 数据和模块脚本中，无法形成可持续运营的产品。

油气知识平台要把这些分散资产转化为一个统一、可信、可检索、可治理、权限可控的内部情报工作平台，让销售与商务人员更快完成客户准备和机会判断，让市场研究团队不依赖代码即可维护内容，并让每项重要事实都能够回溯到来源、权限和变更记录。

## 3. 背景与机会

### 3.1 当前数据与用户规模

当前已确认的近似规模为：

| 领域 | 当前规模 |
|---|---:|
| 公司 | 100+ |
| 项目 | 10,000+ |
| 报告 | 1,111 |
| 报告附件 | 约 1,111 |
| 新闻或公开更新记录 | 1,000+ |
| 每月新增记录 | 至少 1,000 |
| 初始用户 | 约 40 |
| 预期用户 | 100+ |

这一规模并不要求复杂的大型互联网架构，但已经超过人工维护静态页面和多份数据副本所能可靠支撑的范围。

### 3.2 当前核心问题

| 问题 | 对业务的影响 |
|---|---|
| 信息分散在多个页面、地图、文件和脚本中 | 用户需要跨入口拼接答案，客户会前准备耗时且容易遗漏 |
| 公司、项目、报告之间缺少统一标识与关系 | 无法稳定回答“谁参与什么项目、哪些报告支持该判断” |
| 不同模块各自实现搜索、别名和筛选 | 同一查询在不同入口得到不一致结果，跨域检索困难 |
| 数据来源、核验状态、更新时间和历史不可见 | 用户无法快速判断内容是否可信、是否过期 |
| 附件存在公开或永久地址风险 | 授权资料可能被越权预览、下载、导出或二次传播 |
| 内容维护依赖代码或直接修改文件 | 市场研究团队无法形成稳定的导入、审核、发布和纠错闭环 |
| 重复、导入失败和陈旧数据不可见 | 数据问题持续积累，业务对平台失去信任 |
| 过早引入 AI | 在搜索、权限和来源尚未可靠时放大幻觉与泄漏风险 |

### 3.3 产品机会

通过统一入口、标准业务对象、来源治理、权限控制和跨域搜索，平台可以把“找资料”升级为“基于可信证据完成客户和机会决策”，并把当前依赖个人经验与文件管理的流程转变为可度量、可审计、可持续运营的产品能力。

## 4. 产品愿景与定位

### 4.1 产品愿景

> 建立一个连接公司、项目、报告、来源、市场信息和内部分析的油气知识平台，让销售与商务人员更快找到可信信息、准备客户沟通并判断业务机会。

### 4.2 首发定位

- 首发是企业内部产品，不面向匿名访客或外部客户。
- 产品首先服务销售与商务拓展，同时为市场研究、内容审核、管理层和平台管理提供必要工作台。
- 产品价值必须由内部使用效率、内容可信度和持续运营能力证明，不依赖未来商业化或 AI 能力成立。

### 4.3 长期定位

若未来进行商业化，应另行建立外部产品 PRD，并完成数据授权、再分发、租户隔离、合同、计费和外部 AI 使用政策评审。当前产品不得被描述为第三方付费数据库的转售或替代品。

### 4.4 产品原则

1. **单一权威来源：** 生产结构化数据和生产附件各自只有一个受治理的权威来源；Excel、JSON 和旧页面仅是导入、迁移或历史制品。
2. **来源优先：** 每项重要事实必须能够追溯到来源，来源与核验状态是用户可见信息。
3. **权限优先：** 在展示记录、附件、正文片段、导出结果或未来智能答案之前先判断访问权限。
4. **搜索先于 AI：** 先建立精确、可筛选、可解释、可审计的搜索，再评估智能问答。
5. **自动采集、审核发布：** 自动化用于减少重复劳动；敏感、授权受限或重大变化仍需人工审核。
6. **数据质量可见：** 新鲜度、所有者、来源、验证、导入历史和异常状态是产品功能，不是后台隐含信息。
7. **业务对象可复用：** 公司、项目和报告体验必须由统一数据驱动，不再复制公司专属页面。
8. **真实网络体验是发布条件：** 产品必须在目标企业网络中达到性能和可用性标准。
9. **内部价值优先：** 商业化和生产 AI 均不得挤占内部 MVP 的交付质量。

## 5. 产品目标与非目标

### 5.1 产品目标

| ID | 目标 |
|---|---|
| PRD-G-01 | 提供统一的公司、项目和报告知识入口，并建立三者之间可浏览、可搜索的关系 |
| PRD-G-02 | 让销售或商务用户在 5 分钟内找到目标公司、相关项目及支撑报告 |
| PRD-G-03 | 提供跨公司、项目、报告和授权正文的统一搜索与筛选 |
| PRD-G-04 | 让用户在权限范围内预览、下载、分享和导出资料，并保留必要审计记录 |
| PRD-G-05 | 支持收藏、最近查看、保存搜索、关注、站内通知、私人笔记和纠错请求 |
| PRD-G-06 | 让非技术内容维护人员完成导入、校验、查重、审核、发布和数据质量管理 |
| PRD-G-07 | 让所有生产内容具有明确来源、版权类型、安全等级、核验状态、责任方和更新时间 |
| PRD-G-08 | 建立可度量的搜索质量、使用效果、数据新鲜度和运营健康指标 |
| PRD-G-09 | 在不向用户提供 AI 回答的前提下，为未来可追溯、可控权的检索实验准备内容基础 |
| PRD-G-10 | 在公司控制的正式生产入口和目标企业网络中完成内部 MVP 发布、恢复与试点验收 |

### 5.2 当前产品非目标

以下内容不属于内部 MVP：

- 外部客户账号和匿名公开访问。
- 付费订阅、计费和多租户客户隔离。
- CRM 集成。
- 独立新闻中心。
- 面向用户的生产 AI 问答或向量搜索。
- 未经人工审核直接发布的 AI 结论。
- 公共 SEO 网站。
- 原生移动应用。
- 完整 PowerPoint 自动生成。
- 对第三方内容商业再分发权作法律结论。

## 6. 用户、角色与责任

### 6.1 主要用户

#### 销售与商务拓展用户

核心任务：

- 准备客户会议、投标和机会评审。
- 查找公司、项目、报告及其关联证据。
- 关注目标并获取重要变化。
- 收藏、生成内部简报、分享和导出授权内容。
- 提交纠错和补充建议，不直接改写受治理主数据。

#### 市场研究管理员

核心任务：

- 导入、清洗、关联、核验和发布内容。
- 管理来源、分类、别名、重复和数据新鲜度。
- 处理纠错请求、敏感内容和授权资料。
- 监控失败任务、陈旧数据和数据质量。

### 6.2 支持角色

| 角色 | 允许的产品行为 | 关键限制 |
|---|---|---|
| 内容编辑 | 建立和编辑草稿、上传附件、建议关系、提交审核 | 不得自行发布受限内容、修改角色或全局安全政策 |
| 内容审核员 | 批准、拒绝或退回变更，标记核验状态，升级版权或安全问题 | 不得绕过发布审计 |
| 管理层只读用户 | 阅读授权内容、搜索、导出、收藏和关注重点对象 | 不得编辑、审核或发布 |
| 超级管理员 | 管理账号、角色、权限政策、系统配置、审计和保留设置 | 管理权限不自动授予 L4 内容阅读权，内容访问仍需明确授权 |

一个人可以承担多个角色，但角色叠加必须显式授权并可审计。详细“角色 × 动作 × 内容域 × 安全等级”矩阵是产品权限基线：必须以本 PRD 的批准修订形式确定，再由 Product/System Design 表达为页面和流程，不得由下游文档独立决定或弱化。

## 7. 核心用户任务（JTBD）

### PRD-J-01：准备客户会议

当销售人员需要会见目标客户时，希望在一个入口内查看公司概况、业务区域、关键项目、近期变化和相关报告，筛选需要的内容并形成带来源的内部简报，从而减少准备时间并提升沟通质量。

### PRD-J-02：发现项目机会

当商务人员寻找机会时，希望按区域、项目类型、阶段、运营方和容量等条件筛选项目，理解参与方、里程碑和变化，并持续关注目标项目。

### PRD-J-03：找到支撑材料

当用户需要验证一个判断时，希望通过公司、项目、主题或问题式关键词找到报告和授权正文片段，确认来源后预览或下载附件。

### PRD-J-04：提交并闭环纠错

当业务用户发现内容错误时，希望指出具体字段、建议值和来源，由内容团队审核，并能够看到处理结果，而不是直接修改受治理数据。

### PRD-J-05：批量维护并发布内容

当内容团队收到批量数据时，希望完成模板识别、校验、查重、变化预览、暂存、审核和发布，并能够下载错误结果、重试失败任务和追踪每次发布。

## 8. 产品功能范围

### PRD-F-01：统一入口与首页

产品必须提供统一入口，包含：

- 全局搜索。
- 最近更新的公司与项目变化。
- 新发布报告。
- 用户关注对象变化。
- 收藏和常用筛选入口。
- 与内容相关的数据新鲜度和来源提示。

市场价格摘要是可选增强项，不是内部 MVP 的发布阻断项。

### PRD-F-02：公司知识库

产品必须支持：

- 按公司名称和别名搜索。
- 按公司类型、国家、区域、业务板块、市场定位和标签筛选。
- 按名称、更新时间、项目数量或相关性排序。
- 查看公司身份、简介、业务、区域、项目、产量、财务、报告、内部分析、来源和变化历史。
- 将新闻或公开更新作为来源引用或变化事件关联展示，不建立独立新闻中心。
- 查看公司与项目、报告之间的关系。
- 收藏、关注、内部分享、授权导出和提交纠错。

客户跟进记录和内部联系人负责人字段不进入公司主档 MVP。

### PRD-F-03：项目知识库

产品必须支持：

- 按项目名称、别名、区域、国家、盆地、项目类型、阶段、运营方、参与方、容量、状态、来源和更新时间搜索筛选。
- 按更新时间、相关性、阶段或容量排序。
- 查看项目身份、地理位置、容量、状态、阶段、参与公司及角色、里程碑、技术属性、报告、来源和变化历史。
- 通过地图和列表理解项目分布，但不得依赖公开原始数据文件。
- 收藏、关注、内部分享、授权导出和提交纠错。

### PRD-F-04：报告与文档知识库

产品必须支持：

- 按标题、中文标题、摘要、结论、标签、来源、公司、项目和授权正文搜索。
- 按行业、区域、类型、来源、日期、语言、安全等级和核验状态筛选。
- 按相关性、发布日期、上传日期或更新时间排序，并支持可追踪的分页或连续加载。
- 查看来源、出版信息、摘要、结论、标签、关系、版权、安全、版本和提取状态。
- 在权限通过后预览或下载一个或多个附件。
- 确保附件和提取正文的权限不得宽于所属报告或来源。
- 对上传文件执行已批准的类型、大小和内容安全判断；不可安全处理的文件必须隔离，上传内容不得被直接执行，预览必须与主应用隔离。
- 收藏、关注、内部分享和提交纠错。

### PRD-F-05：统一搜索

产品必须：

- 同时检索公司、项目、报告和授权报告正文。
- 支持准确名称、别名、前缀、部分匹配、全文和合理的拼写纠错。
- 提供跨结果类型可理解的筛选、分组和高亮片段。
- 在结果返回前完成权限过滤，避免通过总数、片段或建议词泄漏受限内容。
- 记录搜索、零结果和后续点击，用于持续改进。
- 对搜索分析数据实行最小化收集、受限访问和明确留存；不得把秘密、完整授权内容或不必要的敏感自由文本写入通用日志。
- 对无结果场景提供清晰解释和可继续操作的建议。

“搜索成功”定义为：在产品负责人和市场研究团队批准的代表性查询集中，返回至少一个被评为有用且授权正确的结果；或者当预期确实没有授权结果时，正确说明零结果并提供合理恢复路径。意外零结果不得计为成功。

### PRD-F-06：个人工作流

产品必须支持：

- 收藏。
- 最近查看。
- 保存搜索和筛选视图。
- 关注公司、项目、主题、区域、类型或关键词。
- 订阅保存搜索，并允许用户按对象或订阅静音、调整已批准的站内通知频率。
- 站内通知与通知中心。
- 私人笔记。
- 纠错请求。
- 要求登录并在访问时重新校验权限的内部分享链接。

MVP 只承诺站内通知。系统可保留生成未来摘要所需的记录，但电子邮件发送必须等待身份、邮件和时区政策批准。

通知必须具备优先级、去重和审计。授权管理员必须能够抑制、撤回或解释错误通知事件，避免噪声和错误内容持续传播。

### PRD-F-07：内容治理与发布

产品必须支持：

- 草稿、审核中、已发布和已归档的统一内容生命周期。
- 来源、版权、安全、核验、责任方和更新时间管理。
- 重要事实与来源的可追溯关系。
- 版本历史和重大变化说明。
- 普通、低风险数据在明确规则下自动发布。
- 敏感、授权受限或重大变化必须人工审核。
- 归档或软删除优先，以保留审计链路。

### PRD-F-08：管理与数据运营

授权用户必须能够通过可视化界面完成：

- 公司、项目和报告内容维护。
- 来源、标签、分类和别名维护。
- 批量导入、模板管理、暂存和校验。
- 经批准的定时采集、来源数据接口导入、公开网页复核采集和附件元数据/正文提取；所有方式必须进入同一治理、暂存和审核边界。
- 重复候选处理、审核和发布。
- 纠错请求处理。
- 用户、角色和安全政策管理。
- 审计、数据变化、数据质量和使用效果查看。
- 通知事件查看、抑制、撤回和重处理。
- 失败任务查看和重试。

### PRD-F-09：导出、分享与内部简报

产品必须：

- 支持授权列表的 CSV/XLSX 导出，以及经批准模板的公司或项目 PDF 内部简报。
- 只使用用户当前有权访问且已批准的字段。
- 在导出、生成和打开分享链接时重新检查权限。
- 为 L3/L4 内容保留下载和导出审计；按后续版权动作矩阵决定水印、用户标识和复制限制。
- 在简报中保留来源引用和安全上下文。

内部 MVP 的简报是确定性模板输出，不等同于 AI 自动结论，也不承诺完整 PowerPoint 自动生成。

### PRD-F-10：分析与产品学习

产品必须能够记录并分析：

- 日活、周活和重复使用。
- 搜索次数、成功率、零结果和首次有效点击耗时。
- 公司、项目、报告查看。
- 收藏、关注、简报、预览、下载、纠错和通知处理。
- 导入吞吐、失败、待审核、无来源和陈旧记录。

页面浏览量不得单独作为产品成功指标。

### PRD-F-11：未来检索与 AI 准备

内部 MVP 必须为报告内容保留来源、版本、页面或章节位置以及权限继承信息，使后续可以开展离线检索实验。上述信息必须在报告与文档领域验收时关闭，不能推迟到未来 AI 阶段。

后续“检索准备”阶段只有满足以下结果才可通过：

- 文档分段具有稳定标识和页码/章节引用。
- 每个分段完整继承来源、版本、版权和权限。
- 可以在不向用户展示 AI 答案的前提下完成离线混合检索评估。
- 已建立引用正确性、召回、权限、敏感泄漏和无支持结果的测试集。

该准备不包括：

- 向用户展示向量搜索。
- 生成生产 AI 答案。
- 自动发布 AI 结论。

任何用户可见 AI 功能都需要独立 PRD、离线评测和数据治理批准。

### PRD-F-12：身份与访问结果

产品必须：

- 禁止未经批准的开放注册。
- 允许管理员建立、禁用和回收内部账号。
- 在角色、内容域、安全等级和必要的记录级授权共同满足时才返回内容。
- 对禁用和离职账号立即阻断访问，并保留必要审计。
- 不因用户拥有平台管理权限而自动扩大其敏感内容阅读范围。

具体登录方式、会话策略和企业身份集成属于后续设计与架构决策。

## 9. 业务对象与概念关系

本节定义业务语义，不定义数据库表。

| 业务对象 | 关键关系 |
|---|---|
| 公司 | 与项目多对多关联，关系包含运营方、参与方等角色；可关联报告、来源、指标和标签 |
| 项目 | 可关联多个公司、报告、来源、里程碑、技术属性和变化事件 |
| 报告 | 可关联多个公司和项目，并包含一个或多个附件及授权提取内容 |
| 来源 | 可支撑多个业务记录；一个业务记录也可以引用多个来源 |
| 用户、角色与团队 | 决定模块、动作、安全等级及必要记录范围内的访问结果 |
| 收藏、关注、笔记与保存搜索 | 绑定到标准化业务对象或查询条件，并遵循用户与内容权限 |

| 分类词典 | 区域、国家、公司类型、业务板块、项目类型/阶段、报告类型等跨域统一使用 |

## 10. 权利、安全与治理规则

### 10.1 版权类型

每个来源、生产记录、附件、提取内容和未来检索片段必须具备以下一种版权类型：

- `OWNED`：自有原创。
- `PUBLIC_THIRD_PARTY`：公开第三方。
- `LICENSED_RESTRICTED`：授权受限。
- `DERIVED_REVIEW_REQUIRED`：衍生内容，发布前需审核。

公开第三方信息不等于允许商业再分发。版权类型对应的预览、下载、复制、导出、分享、简报和未来 AI 使用动作矩阵，必须在报告领域建设前由产品负责人、市场研究和法务/合规角色共同批准。

### 10.2 安全等级

- **L1：公开信息。** 这是内容属性；在内部 MVP 中仍要求用户登录，不代表匿名公开访问。
- **L2：内部一般信息。** 普通已授权内部用户可访问。
- **L3：授权订阅受限信息。** 仅限被内部订阅政策覆盖的角色或用户。
- **L4：敏感分析或管理信息。** 需要明确角色或记录级授权。

L3/L4 的下载和导出必须审计。安全等级降级必须记录原因。附件、提取内容、未来检索片段和未来智能输出不得获得比源内容更宽的访问范围。

### 10.3 生产记录必备治理信息

所有可发布生产记录必须具备：

- 来源及来源引用。
- 版权类型。
- 安全等级。
- 核验状态。
- 内容责任方。
- 创建与更新时间。
- 最近复核与下次复核信息，若该领域规定了复核周期。

缺少必备治理信息的导入内容只能进入隔离或草稿状态，不得作为生产已发布内容。

对影响客户判断、机会判断、金额、容量、阶段、参与关系、重要结论或授权范围的“重要事实”，必须提供字段级或结论级来源。对尚未完成字段级迁移的历史内容，可以在明确例外记录下暂用记录级来源，但不得隐藏例外状态。

### 10.4 上传内容安全与行为数据隐私

- 上传内容必须经过已批准的文件类型、大小、文件名和内容安全判断；异常内容进入隔离状态，不得直接执行。
- 附件预览不得让上传内容取得主应用会话或执行权限。
- 下载、导出、预览、搜索和管理操作只收集实现审计与产品改进所必需的数据。
- 通用日志和产品分析不得记录秘密、完整受限正文或与目的无关的敏感自由文本。
- 查询和行为数据的访问、留存、删除与事故处理规则必须在生产前获批。

本节关闭 `PRD-O-20`，定义产品级权限结果；具体权限代码、策略存储和校验顺序由 Product/System Design 与 Technical Architecture 映射，但不得扩大本表。

## 11. 关键业务流程

### 11.1 会前准备

搜索公司 → 查看公司与项目 → 筛选机会 → 查阅授权报告 → 收藏内容 → 生成带来源内部简报 → 内部分享并记录事件。

### 11.2 机会跟踪

筛选项目 → 查看参与方和里程碑 → 关注项目 → 重要变化产生站内通知 → 用户复核变化和来源。

### 11.3 报告查找与使用

查询主题 → 查看报告或授权正文片段 → 按来源、日期、区域筛选 → 打开报告 → 权限判断 → 预览/下载 → 写入审计。

### 11.4 纠错闭环

提交字段与建议值 → 补充来源 → 分配责任人 → 审核 → 接受后形成新版本，拒绝则保留原因 → 通知提交人。

### 11.5 批量导入与发布

上传文件 → 识别模板 → 校验字段与权限信息 → 计算重复候选和变化 → 暂存 → 审核 → 事务性发布 → 更新搜索与关系 → 记录统计和异常。

- 收藏、关注、简报、预览、下载、纠错和通知处理率。
- 导入成功率、重复率、来源完整率和数据新鲜度。

## 13. 发布范围与阶段边界

### 13.1 基础框架

基础框架只建立应用壳、公共契约、身份与权限边界、治理基线、私有文件适配边界、自动化检查和本地开发能力。它是产品建设前提，不构成可供业务验收的完整网站。

### 13.2 内部 MVP

#### 13.2.1 进入生产试点门禁

以下产品能力必须先完成，随后通过 G2、G3 以及 G4 的生产部署与初始 smoke，才可开始约 40 人生产试点：

- 公司、项目和报告三个核心知识域。
- 统一搜索和个人工作流。
- 内容管理、导入、审核和数据质量闭环。
- 前后端、数据、权限和私有附件端到端联通。
- 试点前性能、安全、恢复准备和真实企业网络预验收。

#### 13.2.2 内部 MVP 最终验收

生产试点开始后，必须完成约 40 人试点、达到已批准的采用指标、关闭阻断缺陷并形成产品学习结论。只有 G1-A、G2、G3、G4 和试点后的 G1-B 全部通过，内部 MVP 才可最终验收。

### 13.3 后续检索准备

在内部 MVP 稳定后，可以开展不向用户展示答案的文档分段、权限继承和离线混合检索实验。只有满足 PRD-F-11 的稳定引用、权限继承和离线评测结果，该阶段才可通过；通过不代表生产 AI 获批。

### 13.4 外部产品与生产 AI

外部商业化和用户可见 AI 均需要新的产品决策、独立 PRD、法律与安全审查，不属于本 PRD 的已批准交付。

## 14. 产品分析与试点学习

试点除量化指标外，还必须回答：

1. 哪些信息任务明显变快。
2. 哪些查询仍失败以及失败原因。
3. 用户不信任哪些记录以及原因。
4. 哪些通知有价值、哪些构成噪声。
5. 哪些人工研究工作仍在平台之外。
6. 哪些输出真正用于会议、投标或机会决策。
7. 内容团队是否能够不改代码完成常见维护任务。

## 16. 非规范性附录：文档与实施纠偏结论

本节记录本次治理决策，不增加产品功能、技术选型或 Implementation Task。项目执行状态以文档索引和对应分支记录为准。

**一开始应该单独做 PRD，当前设计规格把 PRD 和技术设计混在了一起，需要补正。**

**现有 10 个 Task 确实包含前端、后端、数据库和测试代码，但只做基础框架。**

**现有 10 个 Task 的验收不是完整 Cloudflare 网站；完整网站要在全部产品阶段完成后，再部署到 Cloudflare 并做生产验收。**

上述第三条是本次纠偏的原始结论。其中“全部产品阶段完成后，再部署到 Cloudflare 并做生产验收”的规范性含义是：先完成所有内部 MVP 产品域，再进入 G4 的 Cloudflare 部署、生产验收和生产试点；试点结束并关闭 G1-B 后，内部 MVP 才最终验收。它不要求在部署前完成试点，也不包含后续 RAG readiness、外部商业化或生产 AI 阶段。

正确流程是先批准本 PRD 和四层验收标准，再依次批准 Product/System Design、Technical Architecture、Roadmap 与 Codex Implementation Plan，最后才开始或恢复对应代码 Task。
