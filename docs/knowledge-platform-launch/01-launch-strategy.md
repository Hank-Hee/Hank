# 知识平台上线策略

## 1. 目标

最短路径不是把所有静态页面直接搬到线上，而是先交付一个可登录、可测试、数据可追溯的内部 UAT 站点，再在稳定契约上扩展完整产品。

本轮的优先级是：

1. 完成 Foundation Task 1A–10，得到可重现的前端、API、数据库治理、身份边界、私有存储适配、CI 和浏览器 smoke 基线。
2. 实施邮箱登录入口和公司知识库纵切，让 10–20 名内部用户能完成真实浏览任务。
3. 用 UAT 证据修正信息密度、数据缺口、页面性能和权限体验。
4. 再完成报告、项目、搜索、个人工作流、管理导入和生产加固。

## 2. 环境定义

| 环境 | 用途 | 数据 | 访问 | 是否可宣称生产交付 |
|---|---|---|---|---|
| Local | 开发、TDD、导入排练、性能基线 | 经挑选的仓库数据 | 本机 | 否 |
| Internal UAT | 10–20 名用户完成真实任务 | 经审核的内部数据快照 | 邮箱登录，非公开 | 否 |
| Production | 正式内部服务 | PostgreSQL 主数据 + R2 主附件 | 正式账号、授权、审计 | 仅 G1–G4 完成后 |

UAT 不能和生产共用未受控的数据库、存储桶或密钥。即使先把 UAT 部署到 Cloudflare，也只能称为受限测试环境。

## 3. 产品边界

当前 Foundation 分支允许：应用壳、三个稳定导航入口、共享契约、公开健康检查、受保护用户上下文、数据库治理基线、R2 适配、自动化测试和本地运行文档。

当前 Foundation 分支不允许：公司/项目/报告业务 schema 与 API、真实内容导入、搜索、通知、AI/向量、生产密钥、真实生产迁移或 Cloudflare 生产发布。

公司 UAT 纵切必须作为 Foundation 后续的单独可审查计划执行，不应被偷塞进 Task 1A–10。

## 4. 故障处理政策

- 指定的 TDD RED 是预期证据，不是阻断。
- 依赖、类型、lint、测试、构建、配置或本地环境失败时，先定位根因，应用最小修复，重跑当前 Task 的完整验证。
- 当个 Task 的所有必需验证未通过前不得提交，但可恢复故障不需向产品负责人逐次请示。
- 同一根因连续三次修复仍失败时，按架构问题升级，不继续猜测式修改。
- 仅在以下情况暂停：可能损坏真实数据；权限、密钥、版权或安全风险；必需的外部账号/凭据/云端权限缺失；权威产品文档存在真实冲突；或三次根因修复表明必须更换架构。

## 5. 交付规则

每个实现 Task 都必须按 RED → GREEN → 完整验证 → 精确提交 → 需求审查 → 代码质量审查执行。普通失败的自动恢复政策不降低“只有全部必需命令通过才能完成 Task”的门禁。

2026-08-03 批准采用精简工程工作流：不再为每个 Task 派发多个实现/审查子代理，也不生成重复的中间审查包。可靠性由以下证据保持：每 Task 细粒度 TDD、全命令门禁、独立 Git 提交、当前 Task 范围的需求/质量复核，以及 Foundation 完成、数据库/授权、登录、数据导入、UAT 上线前的集中独立审查。
